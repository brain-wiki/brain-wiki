# brain-wiki design

Status: **draft for review**. These documents describe what is implemented,
and the implementation follows them;
[14 §1.1](14-roadmap-and-open-questions.md#11-status-2026-10-11) records what is built.
Designs not yet built are in [docs/proposals](../proposals/README.md).
The same documents, as a brain-wiki brain, are in `docs-brain/` (generated by
`scripts/build_docs_brain.py`).

## Decision log

Each decision links to where it is argued. "Alternatives" lists what was
considered and rejected.

| ID | Decision | Alternatives | Where |
|---|---|---|---|
| D1 | The brain directory is the only source of truth; the SQLite index is a rebuildable cache stored outside the brain. | Database as source of truth; index inside the brain | [02 §2](02-brain-format.md#2-directory-layout), [04](04-index-and-retrieval.md) |
| D2 | The repo contains only source. Brains live at user-configured paths, and a user can have several named brains. | Brain inside the repo; one brain per user | [03](03-config-and-storage.md) |
| D3 | Frontmatter is flat (scalars and lists of scalars). Claims and relations are frontmatter lists of strings (`bw-claims`, `bw-<verb>`), so the body stays prose and Obsidian shows them as properties with live links. Format 1 kept them in `## Claims` and `## Relations` body sections. | Nested YAML objects (Obsidian cannot show or edit them); body sections (format 1: data mixed into prose, invisible to the Properties view) | [02 §4, §6](02-brain-format.md#4-common-file-conventions) |
| D4 | Five relation families with eight canonical verbs; domain meaning goes in free qualifiers. | Compass-style poles; per-domain verb vocabularies compiled to families | [02 §6.4](02-brain-format.md#64-relations) |
| D5 | Guard co-retrieval: superseding and conflicting notes are always returned with a hit, in both directions, on top of top-k. | Rank-based retrieval only; post-hoc contradiction reports only | [02 §7](02-brain-format.md#7-guard-relations), [04 §5](04-index-and-retrieval.md#5-guard-co-retrieval) |
| D6 | Three write paths: an append-only inbox open to any agent; curated notes changed through validated ops (consolidation); and direct agent edits that `brain check` validates and records (D28). Human edits are always allowed. | Unchecked direct edits by agents; MCP as the only write path | [05](05-write-path-and-consolidation.md) |
| D7 | The LLM only proposes JSON ops; the engine validates, applies, lints, records undo, and commits. | LLM rewrites whole files | [05 §5](05-write-path-and-consolidation.md#5-operations) |
| D8 | Consolidation reaches an LLM through the host agent (MCP). No API keys in v0.1. | Built-in provider SDKs | [05 §4](05-write-path-and-consolidation.md#4-consolidation) |
| D9 | Provenance, including inputs, is set by the code path that writes, never by model text. Content with external or unknown inputs can never become a rule. | Trust model self-reports | [05 §3](05-write-path-and-consolidation.md#3-provenance-and-inputs), [10](10-security-and-privacy.md) |
| D10 | No access control inside a brain for now: every host that may use a brain reads all of it. Separate brains and host brain limits are the boundary; privacy inside a brain is being redesigned around who receives content. | Ordered levels per note and topic with a maximum per profile, plus topic allowlists (shipped, then removed: a level did not say what it protects against or from whom); unordered label sets; embedding-based classification | [03](03-config-and-storage.md), [10](10-security-and-privacy.md), [privacy proposal](../proposals/privacy.md) |
| D11 | v0.1 storage is a local directory with optional git integration. Remote storage is added later as replicators (git remote, fsspec object stores), keeping a local working copy. | Engine reads object storage directly; required git | [03 §6](03-config-and-storage.md#6-storage-and-sync) |
| D12 | ULIDs identify brains, notes, episodes, claims, rules, and runs; links resolve like Obsidian with id-based repair. | Path-only identity; UUIDv4 | [02 §5](02-brain-format.md#5-identifiers) |
| D13 | Pending vs consolidated episodes is encoded by location (`inbox/` vs `archive/`), not by a watermark file. | Watermark in machine state | [02 §9](02-brain-format.md#9-episodes) |
| D14 | The repo root is also the plugin root for every host; `brain connect` wires local installs; no host lifecycle hooks in v0.1 ([proposal](../proposals/hooks.md)). | Separate repos per host; plugin in a subdirectory | [08](08-agent-integrations.md) |
| D15 | Remote MCP for chat apps is designed but not built in v0.1. | Ship HTTP + OAuth in v0.1 | [proposal](../proposals/remote-mcp.md) |
| D16 | Python ≥ 3.11, stdlib-first, few runtime dependencies. The CLI was on `argparse` for fast startup until D31. | Rust core | [13](13-engineering.md) |
| D17 | The visualizer is a WebGL galaxy with semantic zoom (galaxy → constellation → topic → note), loading topics on demand from `brain viz`'s local server. It is a TypeScript app built with Vite in its own repository (brain-wiki-viz); only the built bundle is committed here, so users never need Node. | One force graph of everything from vendored JavaScript with no build step (the first design); a 2.5D terrain atlas | [12](12-visualizer.md) |
| D18 | The bench uses synthetic, seeded data and deterministic graders; model comparisons run through the headless presets that harvest uses. | Public datasets only; LLM-as-judge by default | [11](11-eval-bench.md) |
| D19 | License: Apache-2.0. | AGPL, MIT | [13](13-engineering.md) |
| D20 | Hosts' own session stores are a second source of episodes (harvest, with backfill) and can be consulted during consolidation (origin lookup); both opt-in, routed by project, and never required for an episode to make sense. Distillation runs in the host agent via an MCP recipe (brain-wiki still reads, filters, routes, scrubs, and sets provenance), headless from the CLI, or raw; hosts without a reader use a self-read fallback with `inputs: unknown`. | Hooks as the only capture path; agents reading raw transcripts themselves for all hosts; copying transcripts into the brain | [05 §2.2, §4.6](05-write-path-and-consolidation.md#22-harvesting-sessions), [08 §6](08-agent-integrations.md#6-harvest) |
| D21 | Gemini CLI is not a supported host. | Shipping a Gemini CLI extension | [08](08-agent-integrations.md) |
| D22 | Three skills (use, setup, maintain) with a guided, resumable onboarding flow; maintenance runs when the user asks. | One broad skill; a terminal-only wizard; scheduled maintenance (built, then removed before 0.1: [proposal](../proposals/scheduled-maintenance.md)) | [15](15-skills-and-onboarding.md) |
| D23 | Plugin MCP entries stay a plain `uvx` command that works on every platform, accepting a slow first start behind a slow package index; `brain connect` is the fast path. | Wrapping the MCP entry in `sh -c` with an installed-command and offline fallback (breaks Windows) | [08 §3](08-agent-integrations.md#3-the-plugin-bundle) |
| D24 | The project lives in the `brain-wiki` GitHub organization (`brain-wiki/brain-wiki`), which sets the plugin manifests' repository fields and the MCP Registry name `io.github.brain-wiki/brain-wiki`. | A personal account | [14 §2](14-roadmap-and-open-questions.md#2-decisions-needed-from-the-maintainer) |
| D25 | Agents learn about brains from static instructions that `brain connect` puts where each host reads them (a rule file, an `AGENTS.md` block, or, for Codex, the MCP server's own instructions); they tell them to call `brain_list` and `brain_orient` when a task may depend on the user's knowledge. No session-start hook delivers the briefing ([proposal](../proposals/hooks.md)). | A session-start hook as the main path (several hosts have no such event) | [08 §3.2](08-agent-integrations.md#32-the-static-instruction-block) |
| D26 | The tools follow progressive discovery (list, orient, search or browse, read with handles, follow relations with `brain_neighbors`) and borrow the Obsidian CLI's conventions: wikilink-style or exact targets, counts and facets before fetching, `paths` output. The CLI mirrors them: `brain search` (an empty query browses), `brain read --mode outline`, `brain neighbors`, and small listings (`links`, `backlinks`, `tags`, `types`, `orphans`, `unresolved`). | One tool per question (every tool description costs context); search only | [04 §6–§9](04-index-and-retrieval.md#6-search), [07 §3.4](07-interfaces.md#34-tools) |
| D27 | Agents may read a brain's files directly, at the folder path `brain_list` gives. | Tools only; the path only for profiles that may read everything (moot while every host reads everything) | [04 §9.1](04-index-and-retrieval.md#91-brain-list), [10](10-security-and-privacy.md) |
| D28 | Agents may edit notes directly when their profile has `edit` and the topic allows it, then run `brain check`, which validates the change (schema, links, claims only superseded, protected files, loss guard) and records it as a run with an undo point. | Episodes and consolidation only (they cannot express prose or property updates); unchecked edits | [05 §2.3](05-write-path-and-consolidation.md#23-checked-agent-edits) |
| D29 | brain-wiki's own frontmatter fields carry a `bw-` prefix: relations, claims, stage, and episode provenance. Shared metadata (`id`, `type`, `title`, `aliases`, `tags`, `status`, `created`, `updated`) stays unprefixed. `format` in `brain.toml` names the newest file format a brain may hold; writers raise it one-way, and older tools refuse to open newer brains. | No prefix (clashes with other tools' properties); a dotted `brain-wiki.` prefix (Dataview reads dots as nesting); best-effort reads of newer brains (an old reader misses `bw-claims`) | [02 §4, §13](02-brain-format.md#4-common-file-conventions) |
| D30 | Topics form a tree: a folder under `topics/` with a hub is a topic at any depth, and its parent is the nearest enclosing topic. A topic is known by a unique slug, not its path, so folders can be reorganized (`brain mv` moves a topic folder). Topic policies (review, agent edits) inherit down; a sub-topic's hub is implicitly `part_of` its parent's hub, so folders and containment relations form one hierarchy. | Flat topics with structure only from relations (cluttered folders, long briefing, guessed map groups); flat topics plus a `group` field (grouping invisible in file browsers); path-based topic ids (break on every reorganization) | [02 §2](02-brain-format.md#2-directory-layout) |
| D31 | The CLI is built on Typer (help in plain text, rich never imported): nested subcommands with their own help, validation from type annotations, and shell completion. Typer only parses; `main` runs the handler and owns exit codes. Its ~50 ms startup cost is accepted now that no hook runs the CLI on every agent turn. (`typer-slim` was the plan, but it is now an alias that installs full `typer`.) | `argparse` with nested subparsers; Click | [07 §2.4](07-interfaces.md#24-parser-and-startup-cost) |
