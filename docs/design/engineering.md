# Engineering

This document covers the repository layout, package structure,
dependencies, packaging, performance budgets, tests, CI, and releases.

## 1. Repository layout

The repository root is also the plugin root for every supported host
([D14](../decision/d14-repo-is-plugin-root.md)), so some root names are
reserved by hosts and hold only plugin content.

```text
brain-wiki/
├── plugin.json                  plugin manifest (Agent Plugins format, with extensions["com.openai"]); also read by Antigravity
├── mcp.json                     MCP server for Agent Plugins hosts (Codex, ChatGPT desktop, OpenClaw)
├── .mcp.json                    MCP server for Claude Code
├── mcp_config.json              MCP server for Antigravity
├── server.json                  MCP Registry entry
├── .claude-plugin/
│   ├── plugin.json              Claude Code plugin manifest
│   └── marketplace.json         marketplace listing this repo as one plugin
├── rules/brain-wiki.md          Antigravity rule (trigger: always_on), generated from the static instruction block
├── skills/                      brain, brain-setup, brain-maintain, shared by all hosts
│
├── src/brainwiki/               the Python package (§2)
├── tests/                       pytest suites; synthetic fixtures in tests/fixtures/
├── docs/                        user/, design/, decision/, roadmap/, proposal/
├── docs-brain/                  docs/ as a brain, generated by scripts/build_docs_brain.py
├── scripts/                     check, visibility, version sync, docs brain, visualizer bundle check
├── .github/workflows/           ci.yml and release.yml
├── pyproject.toml
├── README.md, LICENSE, CONTRIBUTING.md, SECURITY.md, CHANGELOG.md
├── AGENTS.md                    guide for coding agents working on this repository
└── .pre-commit-hooks.yaml       exposes `brain lint --staged` to the pre-commit framework
```

These root names are interpreted by at least one host when the repository
is installed as a plugin, and nothing else may use them: `plugin.json`,
`mcp.json`, `.mcp.json`, `mcp_config.json`, `settings.json`, `.lsp.json`,
`skills/`, `agents/`, `commands/`, `hooks/`, `rules/`, `output-styles/`,
`sidecars/`, `.claude-plugin/`, `.codex-plugin/`, `.cursor-plugin/`.

Developer instructions must not reach users' sessions. Whether any host
loads a plugin-root `AGENTS.md` (or `GEMINI.md`, which Antigravity treats
like `AGENTS.md` in workspaces) into a user's session is unverified. The
repository has no `GEMINI.md`, and its `AGENTS.md` is short and opens with
a line telling any agent that is not developing brain-wiki to ignore it.
Test item T-4 in [verification](../roadmap/verification.md) checks this.

## 2. Package structure

```text
src/brainwiki/
├── cli/            Typer app (_main.py); handlers grouped in _cmd_*.py modules, imported lazily
├── config/         user config, brain.toml, brain resolution, platform directories
├── format/         parsers and writers: frontmatter, links, episodes, rules, the AGENTS.md block;
│                   format 1 and 2 to 3 conversion (_convert.py, with legacy _claims.py and _relations.py)
├── store/          LocalStore: path checks, atomic writes, O_EXCL creates, expected-hash writes
├── index/          SQLite schema, scanner, search, supersession guards, read, neighbors, orientation
├── lint/           rules, profiles, fixes, reports, the pre-commit hook, `brain validate` (_validate.py)
├── write/          episode writer, secret scrubber, rules and proposals, agent profiles, mv, path checks
├── consolidate/    --prepare (_prepare.py) and --done (_done.py)
├── schedule/       `brain commit`, crontab and LaunchAgent jobs, doctor checks for jobs
├── runs/           run transactions, records, pre-images, undo, locks, git integration
├── importer/       overlay, into, to-episodes, from-host
├── mcp/            MCP server, the only package that imports the SDK
├── hosts/          per-host knowledge: session readers, detection, connect writers, instruction blocks
├── viz/            graph export, level-of-detail API, local server; app/ is the built front end (committed)
├── bench/          generator, suites with their graders, report
├── assets/         prompts (consolidate, distill, harvest)
└── *.py            top-level modules: engine, lifecycle, harvest, presets, origin, doctor,
                    setup_wizard, obsidian, ids, errors, logs
```

`presets.py` runs headless host CLIs for harvest distillation. The wheel
also carries the root plugin files under `brainwiki/assets/plugin/` (§4).

Dependency direction (an arrow means "may import"):

```
cli ─► mcp, viz, bench, importer, setup_wizard, doctor
         ─► consolidate, lint, schedule, harvest, origin
               ─► write, runs, index, engine, lifecycle
                     ─► format, store, config, hosts, ids, errors
```

`format`, `store`, `config`, and `hosts` import nothing above them. Only
the CLI imports `mcp`, `viz`, and `bench`, so the MCP SDK, the visualizer,
and the bench stay out of the core.

Package boundaries:

- Every module inside a package is private (`index/_search.py`).
- A package's API is what its `__init__.py` re-exports and lists in
  `__all__`. Code outside the package imports only that: `from
  brainwiki.index import search`, never `brainwiki.index._search`.
- Where a group of operations reads better qualified, the package exports
  the module as a namespace (`from brainwiki.hosts import connect`, then
  `connect.plan(...)`).
- Inside a package, modules import each other's private modules directly,
  never their own package's `__init__`, which loads every module of the
  package.
- The modules directly under `brainwiki/` (`engine`, `errors`, `ids`, and
  the like) stay public. Re-exporting them from the root would load the
  whole package on any import.
- Tests may import private modules.

`scripts/check_visibility.py` enforces these rules, and also that every
re-export is used outside its package and that a module-level name is
public only when another module, a test, or a script uses it, it appears in
a public signature, or it is on the script's short allowlist.

## 3. Dependencies

| Package | Range | Why |
|---|---|---|
| `mcp` | `>=2.3,<3` | MCP server. Imported only by `brainwiki.mcp`. |
| `PyYAML` | `>=6.0` | Frontmatter parsing, with `CSafeLoader` when available. |
| `tomlkit` | `>=0.12` | Editing `config.toml` and `brain.toml` without losing comments. Reading uses stdlib `tomllib`. |
| `filelock` | `>=3.12` | Cross-platform advisory locks. |
| `typer` | `>=0.26,<1` | The CLI parser ([D31](../decision/d31-typer-cli.md), [CLI and MCP §2.4](cli-and-mcp.md#24-parser-and-startup-cost)). |

- `mcp` pulls in pydantic, starlette, uvicorn, httpx2, jsonschema, and
  others.
- Writers edit frontmatter line by line instead of dumping YAML, so
  formatting is preserved.
- `filelock` is imported only when a lock is taken, because it loads
  `asyncio` (about 40 ms), which read-only commands never need.
- `typer` vendors Click and installs rich and shellingham. Rich markup is
  off, so rich is never imported.

Everything else is standard library ([D16](../decision/d16-python-stdlib-first.md)):
`sqlite3`, `tomllib`, `json`, `re`, `hashlib`, `gzip`, `subprocess`,
`http.server`. ULIDs come from a small internal function. There are no
optional extras. A file watcher for long-running processes is in the
[backlog](../roadmap/ideas.md).

Development tools are the `dev` dependency group (`uv sync` installs it):
`pytest>=8`, `hypothesis>=6.100`, and `ruff==0.16.10`. Ruff is pinned
exactly because its formatting changes between releases. `pyproject.toml`
has a pyright section for editors, but no type checker or coverage tool
runs in `scripts/check.py`.

A new runtime dependency needs a reason in its pull request, a compatible
license (Apache-2.0, MIT, BSD, PSF; MPL-2.0 for tools only), and a version
range in `pyproject.toml`. The repository tracks no lockfile; `uv.lock` is
ignored.

Supported Python is 3.11 and newer. SQLite needs FTS5 (`brain doctor`
reports `no_fts5` otherwise). Trigram search (SQLite 3.34+) is used when
present.

## 4. Packaging and distribution

- The build backend is `hatchling`. The wheel force-includes the root
  plugin files (`plugin.json`, `mcp.json`, `.mcp.json`, `mcp_config.json`,
  `server.json`, `.claude-plugin/`, `rules/`, `skills/`) under
  `brainwiki/assets/plugin/`, so `brain connect` installs the same files
  the marketplaces serve.
- The sdist is built from an allowlist in `pyproject.toml`, so local drafts
  and caches never reach it.
- Console scripts are `brain`, `brain-wiki` (the same entry point), and
  `brain-wiki-mcp` (the same as `brain mcp`, for registries and configs
  that expect a dedicated server binary).
- Users are told to install with `uv tool install brain-wiki` or `pipx
  install brain-wiki`, or to run `uvx --from brain-wiki brain …` with no
  install.
- On PyPI, `brain-wiki` is the package. `brainwiki` is published as a thin
  alias that depends on it.
- The README carries the `mcp-name:` marker the MCP Registry uses to verify
  PyPI ownership. `server.json` declares the PyPI package, run with `uvx`
  and the `mcp` argument over stdio.
- The only hand-maintained version is in `pyproject.toml`.
  `scripts/sync_versions.py` writes the release version into the plugin
  manifests, `server.json`, and the `brain-wiki==<version>` pins in the MCP
  configs. It also regenerates the skill references that mirror
  `src/brainwiki/assets/` and the Antigravity rule. CI fails on drift
  (`--check`).
- An npm launcher package (`npx brain-wiki`, delegating to `uvx`) is
  deferred until there is demand.

## 5. Performance budgets

The `perf` bench suite checks these budgets at 10k notes:

| Operation | Budget |
|---|---|
| Freshness check with no changes, p95 | < 150 ms |
| One-file update (write-through), p95 | < 50 ms |
| Search, p95 | < 50 ms |
| Read, p95 | < 20 ms |
| Orientation, p95 | < 30 ms |
| Lint, whole brain, warm | < 1 s |
| Full index rebuild | < 30 s |

See also [index and search §10](index-and-search.md#10-performance-budgets).

- Below 10k notes the thresholds are relaxed 2×.
- The suite is not part of `scripts/check.py`. Run `brain bench perf
  --sizes 10k` for performance work and before a release.
- CLI start-up imports only the module of the command run, and `brain
  --help` imports none of them
  ([CLI and MCP §2.4](cli-and-mcp.md#24-parser-and-startup-cost)). A test
  checks what `brain --help` imports. No check measures time.

## 6. Testing

| Layer | What | How |
|---|---|---|
| Unit | Parsers, writers, format conversion, `brain validate`, link resolution, profiles, path safety | pytest |
| Property | Frontmatter writes never touch the body; quoted values are valid YAML; conversion keeps every claim's text | hypothesis |
| Index | Schema, freshness (edits, renames, deletes), supersession guards in both directions and through chains | pytest on temporary brains |
| Commit and schedule | `brain commit` on temporary git repositories with a local origin; crontab and LaunchAgent backends through an injected command runner | pytest |
| CLI | Commands end to end on temporary brains with `BRAIN_WIKI_*` overrides | pytest, calling `main()` in process |
| MCP | Every tool through the SDK's in-memory client; error codes; schema conformance | `mcp.Client(server)` |
| Session readers | Synthetic sessions per host to normalized turns, routing, inputs | pytest |
| Plugin | Manifests parse and agree; skills follow the Agent Skills rules | `tests/test_plugin.py` |
| Hosts | The plugin loads in real hosts, and smoke flows work | By hand before releases |
| Bench | [Eval bench](eval-bench.md) `retrieval` and `lint` suites on a 300-note brain | `brain bench`, from `scripts/check.py` |

Fixtures are synthetic: a small hand-written example brain about the
fictional notes app Lumen (`tests/fixtures/example-brain/`), plus generated
brains for scale tests. No fixture may contain real personal data.

CI runs on Ubuntu and macOS with Python 3.11 and 3.13 (§8). Windows is
best-effort and not tested in CI.

## 7. Code quality

- `ruff` lints and formats, with rule sets E, F, W, I, B, UP, SIM, and S
  (bandit). The S rules flag `shell=True`, `eval`, and similar calls. Tests
  are exempt from S.
- No type checker runs, and there is no coverage target.
- Core code makes no network calls, except the fetch and push `brain
  commit` asks `git` to make to the brain's own remote. This is a
  convention, not a check.

## 8. Continuous integration

`uv run scripts/check.py` is the one entry point, locally and in CI. It
runs each step and reports pass or fail:

1. `ruff check` and `ruff format --check` on `src`, `tests`, and `scripts`.
2. The test suite (`pytest`).
3. Minimal visibility (`scripts/check_visibility.py`, §2).
4. Version consistency (`scripts/sync_versions.py --check`, §4).
5. The docs brain is current (`scripts/build_docs_brain.py --check`).
6. The visualizer bundle (`scripts/check_viz.py`): the committed bundle is
   complete, and `BUILD_INFO.json` names the brain-wiki-viz commit it was
   built from, from a clean tree.
7. Package contents: builds the wheel and sdist, checks that the wheel
   holds the plugin files, the consolidate prompt, the `brain` skill, and
   the visualizer, and that the sdist holds only allowed top-level entries.
8. The offline bench: `retrieval` and `lint` on a 300-note brain.

GitHub Actions (`ci.yml`) runs on pushes to `main` and on pull requests:

- `scripts/check.py` on Ubuntu and macOS with Python 3.11 and 3.13;
- a visualizer job that checks out brain-wiki-viz at the commit in
  `BUILD_INFO.json`, runs `npm ci` and `npm run check` (type check, unit
  tests, and the public-registry lockfile check, since brain-wiki-viz has no
  CI of its own), then `scripts/check_viz.py --source` to rebuild the
  bundle and fail on any difference.

## 9. Release

1. Set the version, a final `X.Y.Z` or a development release such as
   `X.Y.Z.devN`. Date its `CHANGELOG.md` entry as `## X.Y.Z (YYYY-MM-DD)`,
   run `scripts/sync_versions.py`, and commit.
2. Push `main` and wait for CI to pass. Then push the tag `vX.Y.Z`. There
   is no approval step, so the tag publishes.
3. `.github/workflows/release.yml` checks that the tag matches the version
   and that the changelog has a dated entry, runs `scripts/check.py`,
   builds the sdist and wheel, publishes them to PyPI with trusted
   publishing, and creates the GitHub release from the changelog entry.
4. Move `main` to the next `.devN` version.

- GitHub labels a release the way pip treats it. A dev, alpha, beta, or rc
  version is marked Latest while no final release exists, and a
  pre-release once one does.
- The job that publishes `server.json` to the MCP Registry (GitHub OIDC) is
  turned off until the project decides to be listed, with the repository
  public first. A Registry install gets only the MCP server, and its first
  run depends on the `not_configured` hint leading to `uvx --from
  brain-wiki brain setup --guide`
  ([skills and onboarding §3.1](skills-and-onboarding.md#31-entry-points)).
  When turned on, it lists final versions only.
- The plugin files point at the newest dated release, final or development
  (`scripts/sync_versions.py`). The Claude Code and Codex marketplaces read
  the repository directly, and Antigravity installs from the repository
  URL, so a pin to an unreleased version would break every install.

## 10. Open-source hygiene

- No real personal data anywhere. Examples use a fictional project and
  generic domains, and docs never reference private systems.
- Maintainers may keep a local, untracked denylist of private strings
  (names, hosts, paths) checked by a local pre-commit hook, so private
  context cannot slip into commits. The denylist never enters the
  repository.
- `SECURITY.md` explains how to report vulnerabilities privately.
